# 1. CONTEXTO DEL PRODUCTO

Empresa: ARVOKTA.

Producto: DOVEXO.

DOVEXO es un SaaS B2B para empresas de servicios técnicos a domicilio.

Está orientado inicialmente a:

- Instaladores de aire acondicionado.
- Técnicos de climatización.
- Refrigeración.
- Electricistas.
- Plomeros.
- Empresas de mantenimiento.
- Empresas de instalaciones.
- Servicios de reparación.

Su objetivo es centralizar el circuito de trabajo de estas empresas.

Desde que un cliente solicita un servicio hasta que se realiza el trabajo, se cobra y se actualiza el historial.

El producto dispone de:

- Landing comercial.
- Panel administrativo.
- Dashboard operativo.
- CRM.
- Clientes.
- Solicitudes.
- Órdenes de trabajo.
- Presupuestos.
- Aprobaciones públicas.
- Agenda.
- Técnicos.
- Pagos.
- Automatizaciones.
- Notificaciones.
- Asistente de IA.
- WhatsApp.
- Administración global.
- Portal del cliente.
- PWA para técnicos.
- Aplicación móvil desarrollada en Expo / React Native.

El flujo central es:

Consulta → Solicitud → Orden → Presupuesto → Aprobación → Visita → Trabajo realizado → Pago.

Queremos que todas las interfaces comuniquen visualmente que estos módulos forman parte de un único sistema.

# 4. SISTEMA DE DISEÑO GLOBAL

Esta es una de las tareas más importantes.

Crear un sistema visual único para todo DOVEXO.

La landing, dashboard, PWA y aplicación Android deben sentirse como partes del mismo producto.

No significa que cada plataforma deba implementar exactamente los mismos componentes: cada una debe respetar el mismo lenguaje de diseño.

Crear tokens centralizados.

## 4.1. Paleta de colores propuesta

Utilizar una paleta moderna y sobria.

Colores iniciales:

### Marca principal

- Azul primario: #315EFB.
- Azul oscuro: #1E3A8A.
- Azul profundo: #17243D.
- Azul secundario: #4778FF.

### Colores complementarios

- Turquesa: #11A69A.
- Violeta: #7459D9.
- Cian suave: #4CB7D8.

### Colores de estado

- Éxito: verde.
- Advertencia: ámbar.
- Error: rojo.
- Información: azul.

Definir tonos completos para cada estado.

No utilizar colores arbitrarios por componente.

Los estados deben tener el mismo significado en toda la plataforma.

### Fondos

Modo claro:

- Fondo general: gris azulado muy suave.
- Superficies: blanco.
- Superficies secundarias: gris claro.
- Bordes: gris neutro de bajo contraste.
- Texto principal: azul marino casi negro.
- Texto secundario: gris azulado.

Evaluar un modo oscuro opcional posteriormente.

No desarrollar dos sistemas de diseño independientes.

## 4.2. Tipografía

Evaluar:

- Inter.
- Geist.
- Otra familia moderna si ya existe en el proyecto.

Preferir una familia principal y utilizar pesos diferentes.

Definir:

- Display.
- H1.
- H2.
- H3.
- H4.
- Body.
- Small.
- Caption.
- Labels.
- Numbers.

Utilizar números tabulares para importes, métricas y tablas.

No utilizar demasiados tamaños ni pesos diferentes.

## 4.3. Espaciado

Implementar una escala consistente de espaciado basada en múltiplos de 4 px.

Ejemplo:

- 4 px.
- 8 px.
- 12 px.
- 16 px.
- 20 px.
- 24 px.
- 32 px.
- 40 px.
- 48 px.
- 64 px.

No introducir valores aleatorios constantemente.

## 4.4. Radios y superficies

Definir:

- Inputs: 8–10 px.
- Botones: 8–10 px.
- Cards: 12–16 px.
- Modales: 16–20 px.
- Popovers: 10–12 px.

No redondear todos los elementos excesivamente.

## 4.5. Bordes y sombras

Preferir bordes finos y discretos.

Las sombras deben comunicar profundidad real.

No aplicar shadows fuertes a todas las tarjetas.

Evitar el efecto de tarjetas anidadas indiscriminadamente.

No utilizar glassmorphism en toda la aplicación.

Puede utilizarse en algún elemento de marketing si existe una justificación visual.

## 4.6. Iconografía

Utilizar una única familia coherente de iconos.

Lucide es una opción recomendada si ya está integrada.

Mantener consistencia en:

- Tamaños.
- Stroke.
- Alineación.
- Color.
- Separación.
- Uso dentro de botones.

No utilizar emojis como iconografía principal de la aplicación.

https://saas-gestion-web.vercel.app/

## 5.1. Hero principal

Mantener el concepto comercial:

"Del primer llamado al último cobro, todo en orden."

Mejorar su ejecución visual.

### Layout

Dos columnas.

Columna izquierda:

- Etiqueta de producto.
- Título.
- Descripción breve.
- CTA principal.
- CTA secundario.

Columna derecha:

- Composición visual del producto.
- Dashboard.
- Smartphone.

- Profundidad.

Mobile:

- Título.
- Descripción.
- CTA.
- Mockup debajo.
- Sin composiciones que excedan el ancho.

### Mockup principal

No utilizar una imagen genérica de un cerebro o un robot.

Representar DOVEXO mediante sus propias interfaces.

Composición sugerida:

- Dashboard administrativo como elemento principal.
- Teléfono mostrando una orden asignada.
- Notificación de presupuesto aprobado.
- Elementos de profundidad leves.

Utilizar componentes HTML reales cuando sea posible.

Los mockups deben mantener información coherente.

No mostrar métricas inexistentes ni operaciones presentadas como reales.

## 5.2. Animación narrativa del hero

Crear una secuencia de demostración que comunique el flujo del producto.

Ejemplo:

1. Se recibe una consulta.
2. Se crea una solicitud.
3. Se genera una orden.
4. Se asigna un técnico.
5. Se envía un presupuesto.
6. El cliente lo aprueba.
7. El trabajo se completa.
8. Se registra el pago.

La animación debe ser clara.

No hacer ocho pantallas aparecer desordenadamente.

Utilizar una transición visual que conecte los distintos momentos.

Duración sugerida: 5–7 segundos para una secuencia completa.

No utilizar movimiento permanente sin necesidad.

La secuencia debe poder detenerse o respetar las preferencias de movimiento reducido.

## 5.3. Sección de beneficios

En vez de limitarse a enumerar módulos, organizar beneficios:

- Clientes organizados.
- Trabajos bajo control.
- Presupuestos profesionales.
- Técnicos coordinados.
- Automatización.
- Información inteligente.

Cada beneficio puede tener:

- Título.
- Descripción breve.
- Captura real.
- Composición visual.
- Interacción opcional.

Usar una combinación de secciones alternadas.

No crear doce cards idénticas.

## 5.4. Sección interactiva de demostración

La landing ya utiliza diferentes vistas del producto.

Mejorar esa presentación.

Crear tabs:

- Dashboard.
- Órdenes.
- Presupuestos.
- Agenda.
- Técnico.
- Portal del cliente.

Al cambiar de tab:

- Transición fluida.
- Cambio de captura o componente.
- Indicador de selección.
- Altura estable cuando sea posible.
- Ningún desplazamiento inesperado.

En mobile utilizar un selector desplazable o una presentación vertical.

La demostración debe reutilizar el dataset ilustrativo del producto.

## 5.5. Animaciones de scroll

Implementar animaciones de aparición sutiles:

- Opacity.
- Transform.
- Desplazamientos pequeños.
- Stagger en grupos.
- Animaciones de líneas.
- Cambios de estado.

No hacer que cada párrafo y cada icono tenga una animación diferente.

Crear un lenguaje de movimiento coherente.

Evitar que elementos importantes aparezcan tarde o impidan acceder al contenido.

## 5.6. Elementos 3D

Evaluar la incorporación de un elemento 3D en el hero o en una sección particular.

Concepto:

Representación isométrica de una operación de servicio técnico:

- Edificio.
- Técnico.
- Vehículo.
- Puntos de visita.
- Conexiones entre cliente y empresa.

Debe tener relación directa con el producto.

No crear un objeto 3D abstracto que no comunique nada.

### Tecnologías posibles

Prioridad:

1. SVG.
2. CSS.
3. Imagen prerenderizada.
4. Three.js.
5. Spline.

No incorporar Three.js ni Spline solamente por moda.

Evaluar tamaño del bundle, GPU, mobile y rendimiento.

El 3D debe tener degradación elegante si el dispositivo no puede mostrarlo.

## 5.7. Sección de confianza

Mostrar únicamente características comprobables:

- Separación de datos por empresa.
- Accesos controlados.
- Presupuestos con links seguros.
- Historial.
- Información centralizada.

No inventar certificaciones.

No mostrar logos de clientes sin autorización.

## 5.8. Precios

Mantener la claridad de precios y planes.

Mejorar:

- Jerarquía.
- Comparación.
- Límites.
- Características.
- Acciones.
- Responsive.

No destacar un plan únicamente mediante una enorme tarjeta o gradiente.

Explicar capacidades en lenguaje comprensible.

No mostrar integraciones como disponibles si todavía requieren configuración externa.

- Presupuestos sin respuesta.
- Órdenes sin técnico.

- Trabajos atrasados.
- Saldos pendientes.

- Horario.
- Cliente.
- Técnico.
- Servicio.

## 6.6. Rendimiento

Mostrar gráficos únicamente cuando aporten información.

Posibles gráficos:

- Trabajos completados por período.
- Presupuestos aceptados.
- Ingresos registrados.
- Evolución de solicitudes.

Utilizar un diseño limpio.

No utilizar gráficos circulares de decoración.

No utilizar animaciones fuertes al actualizar datos.

- Capturar screenshots.
- Verificar componentes.
- Comprobar errores visuales.
- Realizar pruebas E2E.

No asumir que una página funciona porque compila.

Utilizar Playwright después de cada modificación visual importante.

### Expo MCP

Utilizar para:

- Consultar documentación Expo.
- Consultar versiones compatibles.
- Inspeccionar aplicaciones.
- Capturar screenshots.
- Interactuar con elementos.
- Abrir React Native DevTools.
- Validar componentes móviles.
- Verificar navegación.
- Probar interacciones.

Antes de utilizar capacidades locales, comprobar SDK, versión y configuración del proyecto.

### Context7 MCP

Utilizar para consultar documentación actualizada de las bibliotecas utilizadas.

Priorizar documentación oficial.

No asumir que ejemplos antiguos siguen vigentes.

### Chrome DevTools MCP

Utilizar cuando sea necesario investigar:

- Errores del navegador.
- Requests.
- Console.
- Performance.
- Rendering.
- Network.
- Traces.
- Screenshots.

No utilizarlo para tareas que Playwright ya resuelve correctamente.

## 2. HERRAMIENTAS DE ANIMACIÓN

Frontend web:

- Motion para transiciones y microinteracciones.
- GSAP para secuencias avanzadas.
- React Three Fiber cuando se necesite renderizado 3D interactivo.

Frontend móvil:

- React Native Reanimated.
- Rive cuando necesitemos animaciones interactivas.
- Lottie/dotLottie para animaciones pequeñas.

No instalar todas las bibliotecas automáticamente.

Inspeccionar primero las dependencias existentes.

## 3. WORKFLOW 3D

Cuando se necesite un recurso 3D:

1. Determinar si realmente aporta valor.
2. Definir el resultado esperado.
3. Elegir Spline o Blender.
4. Crear la escena.
5. Revisar el resultado visual.
6. Ajustar iluminación, materiales y cámara.
7. Optimizar geometría.
8. Optimizar texturas.
9. Exportar en un formato adecuado.
10. Integrar en la aplicación.
11. Comprobar rendimiento.
12. Comprobar responsive.
13. Implementar fallback estático.

No incorporar elementos 3D a dashboards administrativos salvo que exista una razón funcional.

Priorizar el 3D en la landing y en presentaciones comerciales.

## 4. WORKFLOW DE DISEÑO

Antes de modificar una pantalla:

1. Capturar el estado actual.
2. Identificar problemas.
3. Consultar referencias.
4. Definir la solución.
5. Crear o actualizar componentes.
6. Implementar.
7. Capturar nuevamente.
8. Comparar.
9. Corregir.
10. Validar responsive.

No afirmar que una mejora visual está terminada sin haber observado el resultado.

## 5. USO DE AGENTES

Distribuir las tareas de manera lógica:

- Agente de investigación visual.
- Agente de diseño.
- Agente frontend web.
- Agente mobile.
- Agente de pruebas visuales.
- Agente de rendimiento.

Cada agente debe recibir un alcance definido y evitar modificar simultáneamente los mismos archivos.

El agente principal conserva la responsabilidad de integrar y verificar los resultados.

No delegar modificaciones destructivas sin revisión.

## 6. SEGURIDAD

Todos los MCP deben utilizar el principio de mínimo privilegio.

No conceder acceso innecesario a:

- Bases de datos de producción.
- Credenciales.
- Archivos personales.
- Repositorios no relacionados.
- Cuentas externas.

Inspeccionar herramientas de terceros antes de instalarlas.

No aprobar automáticamente operaciones destructivas.

No compartir tokens entre servidores MCP.

No guardar secretos dentro del repositorio.

## 7. PRINCIPIO FINAL

Utilizar las herramientas como extensiones reales de las capacidades de desarrollo.

No simular haber creado escenas, animaciones, prototipos o capturas.

Si una herramienta no está conectada, informar la limitación.

Si una herramienta puede resolver una tarea mejor que generar código manualmente, evaluarla.

El objetivo es conseguir la mayor calidad posible en el frontend de DOVEXO, manteniendo rendimiento, accesibilidad, consistencia y facilidad de mantenimiento.
